## 2. Current architecture (as of commit c421d44)

**The one goal:** HOT LEEDZ. A hot leed = a Booking with a real future date +
venue + zip AND quotable evidence of demand or buying precedent (procedural
completeness alone is explicitly banned from scoring hot — see
`DOCS/PROMPTS.json` judge rules).

**Priority order, enforced in the conductor:** mine the ~2,900 existing
clients for creative re-contact reasons FIRST. Tavily/web discovery is last
resort, currently frozen at zero spend (section 4).

Reasons-first mining loop:
- `server/mcp/reasons/ReasonGenerator.js` — LLM emits seasonal/trajectory/
  referral re-contact reasons as Factlet rows (`source: reason:<kind>`),
  prompt in `REASON_PROMPT.json`, 2h cooldown.
- `server/mcp/reasons/ReasonPlanner.js` — Stage 1 of plan_tasks, turns reasons
  into `MINE_REASON` tasks, suppresses SCRAPE_SOURCE/DISCOVER_SOURCES/
  DRILL_CONTAINER/DRILL_DOWN/LAST_30_DAYS while mining is active. Failed hunts
  retry up to 2x via a failCount map (not "hunted forever").
- `skills/mine-reason.md` + `workerManifest.js` MINE_REASON entry — a spawned
  goose curiosity worker hunts backwards from a reason through `find` DB
  queries to affected clients. Deliberately kept as a multi-turn goose session
  (not collapsed to cheap completions) per explicit user decision — the
  reasoning-token loop is the work, and is the workload most portable to
  future local-model hardware. Do not propose eliminating this LLM step.
- `server/mcp/db.js` `conductorGetReadyTasks()` — while any MINE_REASON task
  is ready/claimed, dispatch ONLY mining tasks, ahead of drills.

Outreach: never freehanded by the chat model. `pipeline enqueue
type:"DRAFT_OUTREACH" bookingId:<id>` routes through the in-process
`server/mcp/workers/DraftOutreachWorker.js`, which drafts (dossier-aware,
re-hire framing when applicable), creates the Gmail draft (draft-only
endpoint, never sends), and synchronously `await`s `mark_sent` at the moment
of drafting. `skills/show-hot-leedz.md` forbids the chat model from calling
`gmail__gmail_send`, `get_config`, or composing email text.

Prompt externalization (standing rule): every LLM prompt lives in an adjunct
JSON file next to its consumer (`{lines:[...], _comment}`), loaded via
`server/mcp/promptLoader.js` `fillPrompt(lines, map)` (function-based
replacement, never string replacement — string replacement corrupts on `$`
patterns). New prompts must follow this pattern; do not inline a prompt string
into a `.js` file.

Model resolution (standing rule): `_llmComplete` in `factlets.js` resolves
`(role && cfg.llmModels[role]) || cfg.llmModel || null`. No hardcoded fallback
models anywhere. Missing config = loud `console.error` + `return null`, never
a silent default. Roles: `judge`, `gate`, `apply`, `draft`, `reason` in
`precrime_config.json` `llm.models`.

## 4b. Mine-first is now REAL (2026-08-10) — and how to tune it
`ReasonPlanner.REHUNT_HOURS` (24h) is the mine-vs-discover ratio dial and the
ONLY knob for it. Reasons rotate through a queue (due again once the last hunt
is that old, worked least-recently-hunted first) instead of being consumed
once. Before this the lane went permanently dry after ~19 hunts, which silently
turned stranger-scraping into the default motion. Shorter = more own-book work;
longer = more discovery. Never re-express this as a task budget of 0.
Known follow-up: `ReasonGenerator` still creates 0 new reasons — its dedup
compares against a 60-day window and the seasonal calendar barely changes, so
every proposal is a near-duplicate. Harmless while the queue rotates, but the
19 reasons cannot refresh until they age out.

## 4d. Bounce handling + datetime storage (2026-08-10)
**A bounce is a CONTACT problem, not a LEAD problem** (user rule). `mark_bounced`
clears the dead address, leaves every booking untouched, resets draftStatus to
'brewing' (never 'sent' — that tombstone asserts we reached them), and queues ONE
DRILL_DOWN per client to hunt a new contact. It must NEVER touch `booked` or
`contacted` rows: a won gig does not un-happen because a mailbox died. The old
behaviour cost 2 won gigs (BOOKED 546→544); both restored, snapshot in
`logs/bounce_damage_repair_2026-08-10.json`.

**Datetime storage is now uniform.** SQLite dynamic typing had let three columns
hold BOTH integer epoch-ms (Prisma) and TEXT ISO strings (an April 2026 raw-SQL
bootstrap): `Client.createdAt` (173), `Booking.createdAt` (37), `Booking.startDate`
(35). SQLite sorts ALL integers before ALL text regardless of date, so every date
filter and `orderBy: createdAt` on those tables returned wrong rows — including 31
past events that could never expire. Migrated to integer epoch-ms; backup at
`SCHEMA/data/leedz_backup_pre_datetime_migration_2026-08-10.sqlite`.
RULE: never write a datetime through raw SQL — always go through Prisma, or the
column silently splits again and every time-based query lies.
